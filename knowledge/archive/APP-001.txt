# Manual APP context packet format · draft 0.1

The unit of transfer is a **concept record**. A record can consolidate a discussion that returned across many turns or threads. Preserve consequential reversals and their reasons in the same record. Keep chronology inside a concept when it explains why the current position exists.

## Packet header

| Field | Meaning |
|---|---|
| Format version | Rules used to interpret this packet |
| Packet ID and revision | Stable ID plus immutable revision |
| Parent | Packet and revision inherited by this handoff |
| Architect identity | Portable role name, here Dhriti |
| Authoring surface and date | Where and when this checkpoint was authored |
| Owner and destination | Decision authority and intended receiving surface |
| Mission and current focus | Durable objective and active work |
| Source coverage | What conversation, memory, and artifacts were available |
| Entry point | Files required to recover the current task |

## Concept header and body

1. **ID, title, status, relations.** Status can be Accepted direction, Proposed, Open, or Superseded. Relations name other concept IDs and explain the dependency.
2. **Question and stakes.** Describe what needed deciding.
3. **Evolution.** Condense the positions, corrections, and why the direction changed. Add dates or source anchors where known.
4. **Current position and authority.** Identify accepted decisions and distinguish architect proposals.
5. **Evidence and actions.** Link artifacts and state what was inspected, executed, or reported by a prior session. Retain source attribution. Attach only what is necessary for recovery or verification.
6. **Open issue and next action.** Say what remains uncertain and who decides or acts.

## Transfer procedure

Send the startup instructions and checkpoint first. Load concept records and evidence on demand. The receiver confirms what it read, reconstructs the current position, and flags contradictions or missing references. Save an amendment as a delta with parent revision, affected concept IDs, rationale, evidence, status and acceptance authority. Keep prior revisions in Git. For any unaccepted difference, preserve both the inherited decision and the proposal.

A role profile carries mission, behavior, decision authority, capabilities, and limits. Capability availability is checked at the receiving surface. This draft records the transfer manually and can later be evaluated as a Git-based communication protocol.

# Spec-to-Simulator playbook profile · proposed

The skill is the entry point. The profile tells Dhriti which actions apply at the current stage, what evidence permits a transition, and when the product owner must decide. The runner validates and executes selected operations. The project checkpoint records active stage, goal, accepted revisions, pending action, available tools, and last transition reason.

| Active stage | Advance when | Return when |
|---|---|---|
| Evidence and scope | The test objective and source basis for the intended behavior are explicit | A specific finding is missing or contradicted |
| Representative spec | The scenario has a versioned requirement, expected behavior, and recorded assumptions | New evidence challenges the expected behavior |
| Feasibility and assembly | One scenario can be exercised and observed with the proposed assembly | A component or interface fails, or the spec cannot support a test |
| Execute and evaluate | Inputs, runtime versions, observations, and verdict are recorded | Execution failure needs an assembly change, or a verdict exposes a criteria ambiguity |
| Review and handoff | The comparison and next action are linked to the checkpoint | Govi requests a new variation or reopens a specific decision |

Enter at the earliest stage with an unmet prerequisite for the current ask. With a usable baseline, a rerun can enter at Execute and evaluate. Focus on one active stage. Advance automatically within approved scope when its exit evidence is present. A return records the gap, target stage, affected artifacts, and the point at which to resume. Keep completed evidence available and revisit only what the change affects. A failed assertion remains a valid result and does not itself reopen the spec.

Ask Govi when selecting an unsupported assumption as an expected behavior, changing scope or accepted criteria, resolving an authority conflict, or taking an action that requires user permission. Save the pending question and resume point. Ordinary probing, replay, and comparison can proceed within approved scope. A tool unavailable on the current surface is recorded as unavailable; route around it if another eligible path exists.

## Tool entry

- Research Loop — find and organize source-linked evidence.
- REA — inspect a compatible authorized artifact for a specific behavior gap.
- Craft Anything — optional coding-agent build/check aid for a candidate panel.
- Knowledge Hub — later connector for prior evidence in Git-backed knowledge.
- Pattern library — retrieve versioned patterns and their applicability.
- Visualizer — later human-facing workspace for assembly and run controls, using the same saved state and operations as the skill.

Example: a five-second no-flow timing variation starts at Execute and evaluate. If the simulator reports the expected alarm and the display does not, reopen the panel integration in feasibility and assembly. If the expected reset behavior is itself unclear, return to the spec and ask Govi only if the evidence leaves a material choice.
